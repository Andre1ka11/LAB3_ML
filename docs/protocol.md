# Протокол общего эксперимента: проект для согласования

Версия банка: `1.0.0-draft`. Перед основным прогоном команда проверяет задачи, завершает три гипотезы и прогнозы, фиксирует банк/промпты/эталоны одним коммитом. Не менять общий протокол отдельно под каждую модель.

## Единицы эксперимента

В банке 40 записей. A/B/C/D/F дают 39 обычных задач; E01 является протоколом классификации и разворачивается в 300 отдельных запросов на модель на язык: 100 строк x (0,5,20 примеров). E01 нельзя просто один раз отправить LLM как текст задания и считать выполненным. Итого основной русский эксперимент: 339 запросов на модель, без pilot и дополнительных гипотез; для четырёх моделей 1356. Английские версии подготовлены, но второй язык обязателен для языковой гипотезы H4, а не для любого выбора гипотез.

Accuracy банка считать по отдельным типам; сводную оценку 39 обычных задач явно подписывать. E01 показывать отдельно по каждому shots-режиму, чтобы сотни строк не подавляли остальные типы. Не использовать 40 как знаменатель accuracy, если E01 не является одной бинарной единицей проверки.

## Запуск

1. Отладить парсинг на P01-P05; не включать их в оценку. Промпт согласовать на всех моделях, не оптимизировать под одного провайдера.
2. Для каждой обычной задачи новый диалог: один общий system prompt + ровно `user_prompt`. История соседних задач не переносится.
3. Основной режим: temperature=0 или минимальная поддерживаемая, никаких web/search/tools. Явно указать thinking mode и ограничения API. Если модель игнорирует temperature, записать это и оговорить несопоставимость режимов; не заявлять фиктивное effective=0.
4. Лимит ответа согласовать до прогона и сделать достаточным для D; например 4096 выходных токенов, если все модели поддерживают. Это верхний предел, не целевое потребление. Обрезанный ответ учитывается как неуспех; не дописывать вручную. Тест подключения с max_output_tokens=64 не подходит для банка.
5. Кэшировать ответы и сохранять исходную строку/объект сразу после каждого вызова. Записывать timestamp, точный model ID, провайдера, параметры, токены, задержку, коды ошибок, версию банка и hash prompt.
6. Сетевые ошибки и 429 можно повторять по заранее согласованному правилу (например, до 3 попыток с backoff). Каждую попытку логировать. Не перезапрашивать неправильный содержательный ответ, чтобы выбрать лучший. Содержательный отказ, невалидный JSON и timeout - разные события.
7. Формат ответа - JSON: `answer`, `explanation`, `confidence` (0-100). Не исправлять смысл ответа при парсинге. Проценты/десятичные запятые нормализовать только по заранее принятому правилу. Проблемы формата считать отдельно и включать в основной denominator как неуспех; дополнительно можно показать точность распарсенных, явно указав выборку.

## Проверка

- A: числовое совпадение в пределах `absolute + relative*abs(reference)`; относительный допуск 1%. A06 класс проверяется точно.
- B: вердикт автоматически, обоснование отдельно по рубрике 0-2. Для 2 требуется корректное обоснование. Boolean не подменять неаргументированным мнением LLM-проверяющего.
- C: два участника независимо, без имени модели, оценивают 0-2 по рубрике. Разумные альтернативы разрешены. Сохранить обе исходные оценки и Cohen kappa; если <0.6, уточнить рубрику и переоценить.
- D: JSON-декодирование строки `answer` допустимо; содержимое кода не редактировать. Запуск первого ответа в отдельном окружении без ключей, личных файлов и доступа к API. Не выполнять неизвестный код автоматически на основной машине. Проверить pass@1, метрики и методологические ошибки раздельно, двумя слепыми проверяющими; для kappa использовать двоичные флаги ошибок или заранее определённую категорию. D07 - явно описательная кластеризация, отсутствие holdout там не ошибка.
- E: 0=benign, 1=malignant. Это отличается от исходной sklearn-кодировки и D08! Использовать готовые train5/train20 и test_features. Никаких test labels, row_id или индексов в prompt. Одни и те же шесть признаков для LLM и baseline. Метрики: F1 класса 1 и balanced accuracy; также accuracy константы. У классических моделей нет zero-shot режима без обучающих данных.
- F: F01-F06 и F08 - числа с тем же допуском; F07 - корректный отказ `insufficient_data` с указанием неизвестной базовой частоты. Ответ «данных недостаточно» здесь является правильным. Пары F_BAYES/F_METRIC/F_HOST сохранять связанными; их мало для сильных статистических заявлений о H1.

## Следующие этапы после получения ответов

Для accuracy - 95% bootstrap CI (1000 ресэмплов задач с возвращением); для сравнения двух моделей на совпадающих задачах - exact McNemar. При анализе пар вариантов учитывать зависимость задач и дополнительно делать парный/кластерный bootstrap по pair_id; не превращать три пары в убедительный вывод о запоминании. Сохранять все seed. Для E resample тестовые строки согласованно между моделями; few-shot демонстрации фиксированы, поэтому интервалы не оценивают вариативность выбора обучающих примеров.

Обязательные графики: model x task type; accuracy с CI; стоимость - accuracy; графики гипотез. Цена правильного ответа рассчитывается по официальным тарифам даже при гранте; реальные списания из кармана и расчётную цену не смешивать. Для локальных моделей фиксировать время, память, квантование, CPU/GPU и RAM/VRAM.

## Ограничения, которые следует проверить и обсудить

Малый банк и малое число задач в типе; публичный датасет E может встречаться в обучении LLM; один фиксированный few-shot набор; зависимость моделей от режима рассуждений и обновлений провайдера; ручная оценка C/D; помощь ИИ при подготовке условий и отсутствие гарантии уникальности формулировок. Это список аспектов методики, а не готовые исследовательские выводы отчёта.
